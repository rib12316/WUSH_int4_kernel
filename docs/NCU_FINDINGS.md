# ncu 实测瓶颈档案 (Nsight Compute 2023.3.1, RTX 2060, WDDM)

## s4 GEMM (M=2048×512×4096, 弱点形状)
- Compute(SM) 31.0% | Memory 20.6% (DRAM 5.9%) → 延迟受限, 非算力/带宽受限
- Theoretical/Achieved Occupancy: 25%/24.96% (48B 行距 → 26KB smem → 2 CTA/SM)
- Issue Slots Busy 27.7%; 最高管线 = FMA 24.5% (逐组 scale 的标量流), tensor 管非最高
- Stall 细分 (cycles/issued inst, 总 7.26):
  long_scoreboard 2.01 (global延迟) > wait 1.56 (mma→I2F→FMA 依赖链)
  > barrier 1.17 (2级流水太浅) > short_scoreboard 0.52 > lg 0.34 > mio 0.26
- 处置实验: 32B行距(occ 37.5%) → 回退(冲突代价>占用收益);
  TN=64(CTA翻倍) → 全面回退(A重读翻倍); 三级流水的编辑未实际生效(替换失配)

## fused WMMA (M=2048×4096)
- SM 39.5% | Memory 39.5% (DRAM 28.8%) | Issue 38.3% | Occ 50%
- 最高管线 = FMA 27.6% → 标量 bf16 装载/变换的指令流瓶颈
- 向量化装载(uint4) → 无变化(转换指令吃平了装载收益)

## 结论 (Turing/sm75 的结构性上限)
1. 逐组 scale 在无 cp.async / 无硬件 scale 的 sm75 上 = 每组 64×(I2F+FMUL+FFMA)
   标量流, FMA 管成为最高管线而 tensor 管饿着 —— 这是与 cuBLAS fp16 (纯
   HMMA, 无 scale) 竞争时的固有税。实测稳定差距: 大M GEMM 0.78-0.97×。
2. decode/小M (M≤4) 靠权重带宽红利(1/4流量)确定赢: 1.07-2.43×。
3. 解锁路径: sm_100 blockscaled MMA (硬件逐组scale, WUSH 官方 5.8× 口径)
   或 sm80+ cp.async+int8TC (QServe 路线)。

## P5 轮 (三级流水 + 胖CTA实验)
- 三级寄存器预取流水 (TM=128): M=4096³ 0.91→0.95-1.11×, M=2048×512 0.78→0.85-1.05×
  (WDDM 噪声带内真实提升); 小 TM 因 +48 寄存器占用崩塌(M=64 1.01→0.75×) →
  if constexpr 分流: TM128 三级 / 小TM 直通, M=64 恢复 1.03-1.42×
- 融合 kernel 胖CTA(GPS=8): 895µs 比基线 661-737µs 更差 —— 组间 barrier 串行化
  消灭了小 CTA 的天然重叠 → GPS 回 1 (机制保留)
- 终态端到端: M=1 2.30×, M=2 1.86×, M=4 1.16×, M=64 1.21× ✓
              M=8 0.68×, M=32 0.85×, 大M 0.40-0.79× ✗
- 剩余缺口结构: (a) 融合kernel 737µs@M=2048 (占端到端60%!, ncu: 双39%利用率,
  小CTA调度受限; 下一步=FTR 64→128 行tile翻倍摊T载入) (b) GEMM 大M 0.98×

## P6 轮 (融合kernel攻坚 + 分派矩阵)
- 融合kernel v2: GPS=8 多组流水 + Xs/Tgs双缓冲 + 单同步/组(已验证 Cs 路径,
  码一致率 1.0): 623µs@M=2048 / 1165µs@M=4096 (旧: 661-737 / 1148-1260)
- 碎片直读(.x[] 布局)实验: 码一致率 0.06 全错(identity-T 也错) → .x[] 累加器
  布局假设与 store_matrix 不一致, 回退 Cs 路径 (负结果存档)
- "248µs 假象" 事故: 整体重写未落盘 + grid 用 GPS 缩小 → 只算 1/8 的组,
  码一致率 0.14 ≈ 1/8 恰是铁证 —— 混合态文件 + 静默替换失败的两连击
- smallm 扩展到 M<=64: M=8/32/64 融合 57-68µs → 15/28/48µs
- 终态 e2e: M=1 2.19× / M=2 1.71× / M=4 1.09× / M=32 ~1.00× ✓
            M=8 0.57× / M=64 0.96× / 2048×512 0.38× / 4096³ 0.83× ✗
- 剩余瓶颈(全部量化): M=8 GEMM 0.62-0.82×(需 split-K); 大M GEMM 0.78-1.07×
  (噪声带内parity) + 融合kernel距带宽地板仍 5-8×(ncu: l1tex 71.9%)

## P7 轮 (split-K + smallm行并行 + Cs-fp16实验)
- split-K (M≤8: TM32 + grid.z=4 + fp32部分和+torch归约): GEMM 0.62-0.82× → 0.90-0.98×
- smallm 行维并行 (grid.y=ceil(M/8)): M=64 融合 42→36µs; M=32 e2e → 0.99×
- Cs→fp16 实验: WMMA 不支持 float碎片→half store (编译错) → 回滚 fp32 (同 S4 限制)
- 终态 e2e: M=1 2.16× / M=2 1.72× / M=4 1.11× / M=32 0.99× ✓~
            M=8 0.71-0.83× / M=64 0.83-0.88× / 2048×512 0.39× / 4096³ 0.84× ✗
- 剩余: 大M融合kernel 568-623µs (l1tex smem放大, WMMA存储限制锁死Cs fp32);
        小M GEMM 噪声带 0.9-1.1× (splitk/占用已做, 剩 launch+尾延迟)

## P7 终态锁定
- GPS=16 实验: M=4096 1159→1081µs 改善但 M=2048 671→738µs 回退(grid.x 减半, 并行度损失)
  → GPS=8 锁定
- smallm 大M实验: 1231/1784µs — σ shuffle 串行链劣于 WMMA 版 → 大M维持 WMMA fused
- 终态: GEMM 单核全形态 0.91-2.24× (7/8 形态 ≥0.95×, 2048×512 0.91× 噪声带内)
        e2e: M=1/2/4/8/32 达标 (1.01-2.37×); M=64 0.80-0.88×;
             2048×512 0.44× / 4096³ 0.96× (缺口=融合kernel 671/1159µs, 地板~75/140µs)

## P8 轮 (v3 纯寄存器融合 kernel —— MIO 墙的最终证据)
- v3.0 (warp认领组×行段, treg驻寄存器, shfl广播变换, warp级σ树): 码一致率1.0,
  922µs@M=2048 — ncu: mio_throttle 7.50 + short_scoreboard 6.14 主导, 占用97%
- v3.1 (双行x打包bf162→单次shfl, 跨lane流量减半): 码一致率1.0, 693/1031µs
- 修复两个设计bug: 高nibble来源(相邻行→同行奇lane), 组号与行段解耦(identity-T隔离)
- 【结构性结论 — 三路实验闭合】WUSH块变换要求每行组 32×32 跨lane数据搬运;
  sm75 的全部跨lane通路(shfl/smem)共用单一 MIO/L1 管线:
    v2 WMMA+smem: l1tex 71.9%, 671µs
    v3.0 纯shfl:  mio_throttle 7.50, 922µs
    v3.1 打包shfl: 693µs
  三种架构收敛于同一墙, 距带宽地板(75µs)仍 9×。
- 2048×512 的算术闭合: 即使融合达完美地板75µs + 现GEMM(0.46-0.49ms),
  e2e=0.54ms vs fp16 0.42-0.51 → 0.78-0.94× —— 需 GEMM 效率(现~50% TC峰)
  与融合同时突破, sm75+WDDM 上不可达。
- 终态: e2e 达标 M=1/2/4 (1.15-2.26×); M=8/32/64 0.82-0.94× (噪声带);
        2048×512 0.39×, 4096³ 0.85× —— 需 sm_80+(cp.async/更高效int4) 或
        sm_100(硬件逐组scale, WUSH官方5.8×口径)硬件验证

## P12 轮 (per-tensor scale 快速路线 — 原生 s4 TC e2e, 用户决策"不计精度")
- 用户决策: 只求算子层加速 → 解锁 per-tensor scale (alpha=sx·sw 在 CUTLASS epilogue
  一次乘回), 无逐组 scale 标量流 → 原生 s4 Tensor Core 直通 (S4c 单核 5.04-6.05×@4096³)
- quant kernel (fast_path.cu): 每线程 32 元素 (4×uint4 读/1×uint4 写),
  实测 285-292 GB/s @ 8-17M 元素 (~87% 带宽地板, 非 e2e 瓶颈)
- 【教训级陷阱 1】CUTLASS device::Gemm::run() 在 smem≥48KB 时**每次 launch** 都调
  cudaFuncSetAttribute (gemm.h:484; 本配置 128×256×128×2级 恰 49152B 必触发) ——
  状态变更 API 在 CUDA Graph 捕获期非法。修复: 绕过 run() 直接 cutlass::Kernel<<<>>>
  + static 一次守卫 (eager 预热先踩掉), 捕获期只剩纯 launch (P12-6 replay 位一致证实)
- 【教训级陷阱 2】交接的 fast_path.cu 有两处 bug 被位对拍抓获: ①段内索引
  bv[e0=h*8+2p] 越出 uint4 段的 8 元素界 (只 h=0 正确); ②inv_scale 误写 7.0/scale
  (应 1.0/scale=7/amax, 整体偏大 7× → ~66% 元素饱和)。"已写完未编译"的 kernel 必须
  从对拍开始, 不能信任
- alpha_ptr 机制: LinearCombination 的 Params.alpha_ptr (linear_combination.h:93,176)
  使 kernel 运行期从设备内存读 alpha → amax→inv→quant→alpha→GEMM 全链驻 GPU,
  单图捕获 (host .item() 同步是 eager 的 ~2× 开销: M=32 0.179→0.077ms)
- e2e 终态 (graph, med5, vs fp16): M=1 1.49 / 2 1.48 / 4 1.70 / 8 1.52 / 16 1.59 /
  32 2.28 / 64 2.34 / 4096³ **3.31** / 2048×512 0.86 —— 8/9 ≥1.0×
- 分派 (fast-graph vs P11 逐组): M=1/2 留守逐组 (2.75/2.07 > 1.49/1.48),
  M≥4 全切 fast; 合并终态 8/9 达标 (唯一欠账 2048×512 0.86× 恰落入 P8 算术闭合
  预测的 0.78-0.94× 结构带 —— sm75 上限, 非 kernel 问题)
- 代价实录: outlier 数据 (15×激活/8×权重通道) e2e 相对误差 99.7% (逐组路线 7.83%)
  —— per-tensor scale 对强 outlier 分布基本不可用, "不计精度"决策的边界条件
- 回归: rtn/S2/S3/S4/S4c/sw1/sw2/sw3/final/p3_final 10/10 绿 (sw3/final/p3_final
  的 wmma 3元组解包是 9-28 遗留断裂, 已随本轮修复对齐现行 2 元组 API)

## P13 轮 (half2 scale 流 + splitk 原子 epilogue —— 论文 INT4 口径的本机收官)
- 用户决策回归路线 A (逐组 G=32 σ 截断, 精度支柱); 数值路径选 stage-flush 混合
  (half2 窗口累加 → fp32 运行累加器, 最接近官方 fp32 累加纪律; 官方无硬件回退
  甚至用 bf16 乘数, 我们的 int4×int32 mma 乘数精确)
- [ncu before @4096³, TM128] **XU 管(转换单元) 49% = 真·最高管**(P1 只报了 FMA 31%,
  XU 被忽视), FMA 31%, tensor 仅 12%, fp16 管 0%; 停顿 wait 56808 > lg_throttle 46k >
  long_scoreboard 40k; issue 32.7%, 占用 25% (181 regs) —— 延迟受限 + 转换流主导
- [SASS 实证] cvt.rn.f16.s32 编译为**单条 I2F.F16**(未降级); |fc|≤1568<2048 → int→half
  精确; 主循环 64 IMMA : 128 I2F.F16 : 64 HMUL2 : 64 HFMA2, flush 编译成打包 HADD2.F32
- [ncu after @4096³] **FMA 31%→12.3%, fp16 管 0%→17.2%** (sm75 确有独立 fp16 管,
  HFMA2/HMUL2 在其上执行 —— 修正了"sm75 无 fp16 管"的预判), XU 49→47% 不动;
  GEMM 4096³ 5.94→5.47ms (**+7.6%**) —— XU 转换流(64 cvt/组, 无打包 int→f16 指令)
  成为唯一主导, ~2× 余量但无指令路径可及 → 按止损线停止该方向
- 【负结果: flush 窗口加宽被寄存器否决】FP∈{4,8} 指令数虽降(192→144/136)但 hacc 成为
  循环携带值: TM128 241→254 regs(调度自由度崩塌, 4096³ 6.37ms 反而劣化 16%),
  TM64 102→133 regs(跌出 2 CTA/SM, M=64/2048×512 劣化 11-24%)。**FP=1 出厂**
  (flush 的 F2F+FADD 被编译器打包成 HADD2.F32, 每指令数模型还省一点)
- [P13b splitk 原子 epilogue] y=zeros + atomicAdd(__half*) 直写, 省掉 yp 部分和链
  (alloc/memset/sum/copy ~3 launch + S·Mp·Np·4B): **M=8 e2e 0.81-0.99 → 1.0-1.27× 跨线**;
  加法序不定 → 容差闸门(实测 replay 偏差 0); yp 路径保留为回退开关
- [分派复调] M≤32: tm32+S4; M=64: tm64+S2 + **v3.1 融合链**(反直觉: v3.1 融合单核
  35.6µs 比 smallm 18.6µs 慢, 但整链 219 vs 272µs —— 融合输出布局对 GEMM 下游的影响
  主导); M=64 e2e 绝对值稳定 ~215µs, 比值 0.76-1.10 随 fp16 分母(163-199µs)摆动
- [存量 bug 顺手修] splitk 分支 y.copy_(sum.narrow(N)) 在 N%128≠0 形状不匹配
  (既往测试形态全是 128 倍数从未触发, fp64 仲裁抓获)
- outlier e2e 精度: **7.807% (基线 7.83%, 闸门 8.2%)** —— stage-flush 数值代价为零,
  精度支柱完好; 全回归 12/12 绿 (含 P12)
- 9 形态 e2e 终态: M=1 2.7 / 2 1.6-2.1 / 4 1.2-1.3 / **8 1.0-1.27** / 16 0.87-1.18(带) /
  32 1.2-1.43 / 64 0.76-1.10(分母带) / 4096³ 0.83-0.85 / 2048×512 0.37-0.50(结构闭合)
- [官方口径形态表 exp_p13_official.py, vs fp16 cuBLAS] 真实 LLM 层:
  Qwen3-8B (4096,24576): M=1 **3.07×** / 8 1.37 / 32 1.16 / 64 1.00;
  Llama-70B (8192,57344): M=1 **3.14×** / 8 1.30 / 32 1.31 / 64 1.03;
  (8192,8192): M=32 1.66 / 64 1.25; prefill M≥128 全形态 0.64-0.96× (fp16 饱和
  ~25TF/s vs int4 e2e ~21TF/s —— 逐组 scale 税+融合开销, P8 结论维持)
- 结论: 论文口径下 decode/小 M 段 (真实 LLM 宽 N 层 = 算力主体) 达 **1.0-3.14×**,
  prefill 段 0.8-0.9× 结构带内; 本机 (sm75) 路线 A 杠杆至此用尽 —— XU 转换墙 +
  MIO 融合墙 + 大 M 算术墙三墙均有 ncu/算术证据, 升级硬件是唯一解锁路径
